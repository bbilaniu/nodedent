## Dependency Review Procedure

The reviewer must:

1. Recreate the inventory from the bound npm lockfile and reconcile all direct
   and transitive runtime, development, optional, and build dependencies.
2. Verify registry source, integrity metadata, lockfile consistency, install
   scripts, and unexpected Git, file, or non-registry sources.
3. Run a current advisory scan using a clinic-approved service and record the
   query time, advisory-database freshness, command/tool version, and full
   controlled report reference.
4. Review advisories that automated severity filters omit or downgrade.
5. Determine whether each finding is runtime reachable, build-time reachable,
   development-only, optional-platform-only, or not reachable in the reviewed
   deployment.
6. Review dependency maintainership, release provenance, major-version changes,
   and known supply-chain concerns for the direct runtime and build boundary.
7. Confirm that the deployed artifact was built from the reviewed lockfile using
   the recorded CI workflow and Node/npm versions.
8. Record a remediation, approved compensating control, time-limited risk
   acceptance, or rejection for every finding.

## Threat Review Procedure

The reviewer must independently challenge:

- whether chart number, clinical facts, generated notes, workflow events,
  backups, exports, passphrase/key, browser metadata, and EMR transfer integrity
  are all represented as assets;
- the static origin, Cloudflare/GitHub delivery path, build pipeline, browser
  profile/IndexedDB, unlocked memory, device/OS, extensions, clipboard,
  Downloads, backup locations, and EMR as trust boundaries;
- malicious same-origin code, supply-chain compromise, XSS, hostile extensions,
  endpoint malware, physical access, authorized misuse, stale tabs, storage
  eviction/corruption, backup tampering, passphrase loss, wrong-chart handoff,
  and unavailable/downtime scenarios;
- whether `connect-src 'none'`, encrypted local storage, memory-only keys,
  locking, authenticated backup/restore, revision checks, warnings, manual EMR
  verification, and clinic procedures mitigate the stated threats as claimed;
- whether exclusions such as multi-user authorization, identity-grade audit
  trails, server storage, synchronization, and structured EMR integration are
  acceptable for the intended use;
- whether the device/browser baseline, retention, deletion, backup, incident,
  downtime, training, collection notice, and PIA controls are enforceable;
- whether any residual risk should block release or require a time-limited
  acceptance and re-review trigger.
